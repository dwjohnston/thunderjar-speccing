# Thunderjar landscape research

*Research snapshot: sources checked 22 October 2026. Requested report filename: 23 October 2026.*

**Thunderjar has a real peer group.** Teams are evaluating coding agents on repository tasks, and several open-source tools already compare models, harnesses, and instructions. The strongest reason to build Thunderjar is more specific: the [motivation](../spec/010-motivation.md) asks whether a coding setup still works **on your codebase**, which change affected it, and whether an old result can be inspected and measured again.

This report treats Thunderjar as a **proposed design**, not a shipped product. Its test case varies a base image, code state, repository prompt files, harness/model pair, and initial prompt; it repeats runs in Docker, measures the resulting code, and proposes preserving the finished image for later measurement and restoration. See the [test-case matrix](../spec/055-declaring-test-cases.md), [results](../spec/085-test-case-results.md), and [restore design](../spec/090-restore-purge.md).

## What companies publicly say they use

| Organization | Documented practice | What it establishes |
|---|---|---|
| **Anthropic** | Claude Code uses internal evaluations for behaviors including file edits and overengineering. In April 2026, changes to reasoning defaults, session caching, and a system prompt caused quality complaints that its initial evaluations missed; broader tests found a **3% coding decline** from the prompt change. | Apparent “model drift” can come from the surrounding product. This incident provides **no evidence of intentional model degradation**. [Eval methodology](https://www.anthropic.com/research/demystifying-evals-for-ai-agents); [postmortem](https://www.anthropic.com/research/april-23-postmortem). |
| **Cursor** | CursorBench takes tasks from real internal Cursor sessions and assesses correctness, code quality, efficiency, and interaction behavior. Cursor also checks controlled live traffic because offline grades can miss a worse developer experience. | Real usage tasks and multiple outcome measures matter. CursorBench is internal. [Cursor’s account](https://cursor.com/blog/cursorbench). |
| **GitHub Copilot** | Its private CheckpointBench replays sessions anchored to an immutable public-repository commit. GitHub also published comparisons across Copilot, Claude Code, and Codex, using five independent runs per model. | Repository replay, fixed starting states, harness comparisons, and repetition are established industry practice. [CheckpointBench](https://github.blog/ai-and-ml/project-hydrafusion-frontier-quality-via-multi-model-orchestration/); [comparison methodology](https://github.blog/ai-and-ml/github-copilot/evaluating-performance-and-efficiency-of-the-github-copilot-agentic-harness-across-models-and-tasks/). |
| **OpenAI** | OpenAI describes internal coding tasks derived from pull requests: the agent starts before the change, edits the repository, and is graded with tests. It also reported an audit estimating that roughly **30% of SWE-Bench Pro tasks** have material task or grading problems. | Real repository tasks need careful, revisable graders; a pass rate is only as trustworthy as its tasks. [Internal-task description](https://deploymentsafety.openai.com/chatgpt-agent/watch-mode); [benchmark audit](https://openai.com/index/separating-signal-from-noise-coding-evaluations/). |
| **Sourcegraph** | CodeScaleBench uses large and multi-repository engineering tasks to compare an agent with local tools against one with Sourcegraph retrieval, recording results and transcripts. | Tool and context changes are experimental variables alongside the model. [CodeScaleBench write-up](https://sourcegraph.com/blog/codescalebench-testing-coding-agents-on-large-codebases-and-multi-repo-software-engineering-tasks). |

There is evidence for the *unmet measurement need*, too. In a qualitative [Google Research study](https://research.google/pubs/from-black-box-to-toolbox-human-centered-explainability-in-developer-authored-agent-rules/), all **12 interviewed developers** relied on informal checks to judge whether their repository rule files helped. That is a small interview study, not a measure of industry prevalence.

## Tools closest to Thunderjar

| Tool | Substantial overlap | Main distinction from the Thunderjar spec |
|---|---|---|
| **[UiPath Coder Eval](https://github.com/UiPath/coder_eval)** | User-authored tasks, isolated execution, file and rubric checks, skill activation checks, prompt/model/harness A/B tests, telemetry, and CI. | Probably the closest **task-authoring product** to try first. Its published workflow emphasizes scoring and CI; I did not find Thunderjar’s proposed preserved postrun-image and later measurement workflow in its documentation. |
| **[Harbor](https://github.com/harbor-framework/harbor)** | Custom tasks with Docker environments and verifiers; many coding-agent adapters; multiple attempts and result artifacts. | A powerful **evaluation substrate**. Thunderjar’s repository-specific parameter identity, prompt-file overlays, and historical restore workflow are a more opinionated layer. [Task format](https://github.com/harbor-framework/harbor/blob/main/docs/content/docs/tasks/index.mdx). |
| **[Inspect AI + Inspect SWE](https://inspect.aisi.org.uk/tutorial.html)** | Runs real Claude Code, Codex CLI, or Gemini CLI in a sandbox, with custom datasets, scorers, logs, and comparisons across models. | A flexible research framework requiring the user to assemble the repository workflow. |
| **[Promptfoo](https://www.promptfoo.dev/docs/guides/evaluate-coding-agents/)** | Coding-agent providers, prompt comparisons, assertions against edited files, and a fresh cloned or copied workspace per evaluation. | Its documented isolated workspace is removed after assertions; Thunderjar proposes keeping the complete finished environment so future measurements can inspect it. |

## Less prominent GitHub projects worth watching

- **[CodeProbe](https://github.com/sjarmak/codeprobe)** is unusually close to Thunderjar’s motivation. It mines a repository’s merged changes into tasks, reconstructs prior code states, compares agent/model/tool/preamble configurations, tracks cost, and plots per-task results over commit history. Its documented repository-edit support is **Claude Code supported, Copilot preview, Codex unsupported**. It already covers longitudinal analysis, so that alone is not a Thunderjar differentiator.
- **[SelfBench](https://github.com/mupt-ai/self-bench)** turns a team’s merged PRs into private Harbor tasks with hidden tests and compares model/harness accuracy against cost. It validates candidate tasks before accepting them, a useful answer to the hard problem of creating trustworthy graders.
- **[RepoTrials](https://github.com/PozziTiv4ik/Repo-Trials)** also mines a repository’s own Git history into reproducible coding tasks. It is an early, narrower option worth tracking.
- **[Microsoft Waza](https://github.com/microsoft/waza)** evaluates agent skills and workflows with repeated trials, graders, model comparisons, and saved evidence. **[agent-skill-eval](https://github.com/tardigrde/agent-skill-eval)** runs real coding CLIs with and without a skill and can regrade saved outputs. These focus on skills rather than Thunderjar’s entire code/prompt/harness matrix.
- **[cc-bench](https://github.com/Galou3/cc-bench)** directly asks whether `CLAUDE.md` or `AGENTS.md` helps on your tasks. It offers repeated A/B runs, a placebo condition, and confidence intervals. Its README calls it **alpha** and says its showcased numerical result comes from a mock agent.
- **[Driftproof](https://github.com/driftproofhq/driftproof)** records dated, model-bound skill-evaluation receipts and compares them across releases. This is the closest match to the *slow drift* question, though its scope is skills rather than full repository coding runs.

These are descriptions verified against project documentation, **not hands-on assessments** of reliability or adoption. Several projects document features on their current main branch that may differ from an installed release.

## What the discussion and research say

1. **Measure the complete agent setup.** An [experimental harness study](https://arxiv.org/abs/2607.22585) found large differences in tokens per solved task across harnesses with the model held fixed, while many pass-rate differences remained uncertain. [OpenAI’s harness-aware evaluation example](https://developers.openai.com/cookbook/examples/partners/harness_aware_plugin_evals/harness_aware_plugin_evals) likewise shows that model rankings can change with the agent loop. The right comparison unit for Thunderjar is the **harness/model pair under stated settings**, as its spec proposes.

2. **Repeat runs before interpreting small changes.** A [60,000-trajectory study](https://arxiv.org/abs/2602.07150) found that choosing a single run changed reported pass rates by 2.2–6.0 percentage points, including at temperature zero. Anthropic found a [six-point Terminal-Bench difference](https://www.anthropic.com/research/infrastructure-noise) from infrastructure settings with model, harness, and tasks held fixed. Repetition is already in Thunderjar’s spec; resource settings and uncertainty will also affect whether its comparisons are persuasive.

3. **Instructions need their own experiments.** An [AGENTS.md study](https://arxiv.org/abs/2602.11988) found no general task-success gain from repository context files in its tested settings, while inference cost rose by over 20%. In a small [self-reported repository experiment](https://www.stet.sh/blog/how-i-used-codex-to-improve-its-own-agents-md), a revised instruction file won on five tuning tasks but regressed on a ten-task holdout despite tests staying green. The author explicitly says the result is not statistically significant. Both support measuring prompt-file effects on **quality and cost**, with held-out tasks.

4. **Forum participants question what a benchmark actually measures.** A [Hacker News discussion](https://news.ycombinator.com/item?id=44874736) disputes whether benchmark-specific scaffolds and internal retries describe the agent users receive. In a [skill-evaluation discussion](https://www.reddit.com/r/ClaudeCode/comments/1wlkcbx/skills_are_the_new_code_evals_discussion/), a practitioner points out that telling an agent “use skill X” tests its ability to use the skill, but does not test whether an ordinary request triggers it. These are practitioner observations, not controlled findings.

## Implications for Thunderjar

**The strongest positioning I found is:** *a repeatable experiment over the coding setup a developer actually uses in their repository, with inspectable historical outcomes.* CodeProbe and Coder Eval already cover much of the comparison story. In the projects reviewed, Thunderjar’s proposed combination of **content-addressed inputs, complete preserved postrun images, selective measurement backfill, and restoration to a branch** is less commonly documented. That is a finding about the reviewed sources, not a claim of uniqueness. See Thunderjar’s [parameter identity](../spec/060-test-case-parameters.md), [backfill](../spec/085-test-case-results.md), and [restore](../spec/090-restore-purge.md) designs.

Three spec choices deserve attention if the goal is to *catch* slow degradation:

- **Detection:** v1 explicitly has [no regression verdict or threshold](../spec/020-goals-non-goals.md). It can present comparisons, but a scheduled run cannot itself decide that quality crossed a line.
- **Attribution:** v1 also defers [transcripts and traces](../spec/020-goals-non-goals.md). Outcome measurements can show a change, but diagnosing *why* the agent changed behavior will be harder.
- **Experimental control:** v1 sets [no CPU or memory limit](../spec/020-goals-non-goals.md). Anthropic’s infrastructure result shows that recording or controlling those conditions matters when interpreting small differences.

The research supports Thunderjar’s core question. It also narrows the “model nerfing” hypothesis: a repeated score drop is evidence of a changed **observed system**, not proof that the provider changed the model. Holding code, prompt files, harness version, settings, and runtime conditions fixed gives the investigation a much stronger starting point.
