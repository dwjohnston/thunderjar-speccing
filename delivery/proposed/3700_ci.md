# 3700: CI

A team can run Thunderjar from a scheduled CI job without anyone watching. Every command that reports takes `--json` and prints one JSON document on stdout. Exit codes separate a broken configuration from a broken environment, and a failed agent from either. Thunderjar ships an example GitHub Actions workflow that runs a test case weekly and writes the results to the job summary. It also gives a developer the IDs they need to `show`, `compare` and `restore` the run. This is backlog story 29.

Areas: F

## Spec

- [040-user-experience.md](../../spec/040-user-experience.md#ci-workflows): CI runs on a cadence, is non-interactive, and reports through an exit code plus a JSON summary. It hands off to a developer for [regression triage](../../spec/040-user-experience.md#regression-triage)
- [100-cli-reference.md](../../spec/100-cli-reference.md#conventions): `--json` on every command that reports, and distinct exit codes for success, configuration errors and infrastructure errors
- [020-goals-non-goals.md](../../spec/020-goals-non-goals.md#non-goals-v1): no notion of a regression and no exit code for one, so differences and failed agents still exit 0
- [050-setup-and-configure.md](../../spec/050-setup-and-configure.md#prerequisites): full-history checkout, `docker login` before the run, and credentials from the CI secret store
- [120-test-boundaries.md](../../spec/120-test-boundaries.md#real-harness-smoke-test): the non-blocking smoke test, now on a schedule

## Artifacts

- **Exit codes**, in `src/cli/exit-codes.ts`. Commands throw typed errors (`UsageError`, `ConfigurationError`, `InfrastructureError`), and the entry point maps each one with the pure `exitCodeFor(error): ExitCode`. All commands share these codes:

  | Code | Meaning | Examples |
  |---|---|---|
  | 0 | success | a run where agents failed or timed out ([3100](../3100_failure-handling.md)), a `compare` that finds differences |
  | 1 | unexpected error | an uncaught exception, which is a Thunderjar bug |
  | 2 | usage | bad arguments, or an unknown test case, execution ID or tag |
  | 3 | configuration | anything [1400](../delivered/1400_validation.md) rejects, or any other problem inside `.thunderjar/` |
  | 4 | infrastructure | Docker unreachable, a failed build or push, a failed `determineHash` command, an unset `requiredEnv` or `urlEnv`, an unreachable store, a measurement container that won't start, a postrun image `remeasure` skipped, or a failed removal in `purge` |

  The rule for anything not listed: a problem in `.thunderjar/` is configuration, and a problem in the machine or its services is infrastructure. Every place earlier stories wrote "exits non-zero" now picks one of these codes. `doctor` exits 3 if the configuration check fails, and otherwise 4 if any check fails.
- **`--json`** on `plan`, `run` (and `run --dry-run`), `executions`, `show`, `compare`, `remeasure`, `restore`, `doctor` and `purge`. `init` and `generate` don't take it.
  - With `--json`, stdout carries exactly one JSON document, and progress lines go to stderr, so a CI log still streams progress. An error is printed as `{ "schemaVersion": 1, "error": { "kind", "message" } }`, with the matching exit code. A partial failure (exit 4 after `run` or `remeasure` carried on) still prints the full document, with the problems listed in an `errors` array.
  - Each document has `schemaVersion: 1` and `command`. Values are the stored values (`{ "passed": 4, "failed": 1 }`, `true`, `"skipped"`), not display strings. Durations are in ms and costs are numbers in USD.
  - The documents are built from the functions earlier stories already have (`aggregatePermutation`, `diffParameters`, `pairPermutations`, `compareMeasures`, `planRemeasure`, `planPurge`), through one serialiser per command (`toRunJson(…)`, `toShowExecutionJson(…)` and so on), so the JSON and human output can't disagree. Their TypeScript types are exported from the package for users who script in TS.
  - No secret appears in any JSON document. Store URLs are shown through `redactUrl` ([3500](3500_shared-data-store.md)), and `requiredEnv` values are never included.
- **Non-interactive output.** Nothing prompts. Human output only appends lines, one per iteration as it finishes, and never redraws them. Colour is used only when stdout is a TTY and `NO_COLOR` is unset.
- **Example workflow** `examples/github-actions/thunderjar.yml`, shown on a new "Running in CI" docs page:
  - It runs on `schedule` (weekly) and `workflow_dispatch`.
  - It checks out with `fetch-depth: 0`, so `determineHash` commands such as `git rev-parse origin/main` ([2600](../2600_floating-parameters.md)) resolve against refs fetched when the job starts.
  - It installs, runs `docker login` to the image store, runs `thunderjar doctor`, then runs `thunderjar run <test case> --json > thunderjar-run.json`, with `ANTHROPIC_API_KEY` and `THUNDERJAR_DB_URL` taken from secrets.
  - It appends `thunderjar show <execution>` to `$GITHUB_STEP_SUMMARY`. It finds the previous execution with `executions --json` and appends a `thunderjar compare <previous> <this>`. It uploads the JSON as an artifact.
  - The page says that CI's runs only reach developers if `imageStore` ([3400](3400_registry.md)) and `postgresStore` ([3500](3500_shared-data-store.md)) are set. Without them, the example uploads `.thunderjar/.data/runs.sqlite` as an artifact instead, which is 071's "pass the file around".
- **Thunderjar's own CI** gains `.github/workflows/smoke.yml`, which runs `bun run test:smoke` ([3300](3300_real-harness.md)) weekly and on demand with the `ANTHROPIC_API_KEY` secret. It is not a required check, and a failure doesn't block merges.

Out of scope (story numbers are backlog positions): workflows for other CI providers; a `--fail-on` or threshold option (020's no-regressions non-goal); posting results to pull requests or chat; recording whether CI or a developer ran an execution (3500's `ranBy` question); narrowing a run to one permutation (still open in 100); and the interactive report (story 30).

**Spec gaps.**

- 100 names three exit codes. This story adds usage (2) and unexpected (1), because "unknown execution ID" is neither a configuration problem nor an infrastructure problem. 100 should list all five, plus the rule for anything not listed.
- No page defines the JSON documents' shapes, their versioning, or where errors go under `--json`. 110 says only that `--json` "is not shown here".
- 040 says CI "surfaces loudly" a change in a pinned test case, but 020 rules out a regression exit code. This story surfaces changes through the job summary (`show` and `compare`), not through the exit code. 040 should say so.
- 050 says secrets come from "the CI secret store", but no page describes a CI setup end to end (registry login, shared store, full-history checkout). The new docs page fills that gap, and 040 could link to it.

## How to test

Follow [the delivery testing strategy](../testing-strategy.md) for fixtures, test placement, adapters and cleanup.

- Unit tests (layer 1 of [120](../../spec/120-test-boundaries.md#1-pure-units)): `exitCodeFor` for each error type and an unknown throw. Each `to…Json` serialiser is checked against the same inputs as its human output's tests, including stored `skipped` and errored values and a run that was never measured.
- CLI tests follow [the delivery testing strategy](../testing-strategy.md). Invoke the real CLI against unchanged checked-in scenarios, using recording adapters and external writable stores. Historical JSON cases come from fixed records, not generated executions or patched declarations; fresh `run` cases normalize only variable IDs, paths and timings. Expected JSON values live in the tests. Assert stdout, stderr, exit code and persisted state:
  - for each command in the list, `--json` stdout parses as exactly one document, with `schemaVersion` and `command`, and nothing else on stdout. A snapshot per command covers the fixture scenarios from earlier stories.
  - exit codes: an unknown ID gives 2, a fixture project with a broken declaration gives 3, an unreachable recording Docker adapter gives 4, `run fake-is-prime-failures` gives 0, and `compare` across 2600's moved `main` gives 0
  - an error under `--json` prints the error document. A partial failure prints the full document, a non-empty `errors` and exit 4.
  - the `FAKE_AGENT_TOKEN` sentinel ([3300](3300_real-harness.md)) and a store password appear in no JSON output
  - with stdout not a TTY, the output contains no ANSI escapes
  - every `thunderjar …` line in `examples/github-actions/thunderjar.yml` parses as a valid command and options
- `bun test`
- `bun run typecheck`
- 👷‍♂️ Trigger `smoke.yml` by hand once and check that it passes.

- 👷‍♂️ Add `ANTHROPIC_API_KEY` as a secret in Thunderjar's own repository for `smoke.yml`, ideally from a workspace with a low spend limit.
