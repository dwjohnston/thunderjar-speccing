# 2200: Show results

`thunderjar show <test case | execution>` reads an execution back from the run data store and prints, for each permutation, a table of every stored measure in each iteration. `thunderjar show <container run>` prints one run: its parameters, measures, exit code and duration. This is backlog story 14 ("report"), built as the spec's `show` command.

Areas: E, F

## Spec

- [100-cli-reference.md](../spec/100-cli-reference.md#show) — `show` usage, the two kinds of ID it takes, and a test case name meaning its latest execution
- [110-cli-report-visualization.md](../spec/110-cli-report-visualization.md#show) — example output for an execution and for a container run

## Artifacts

- Two new read methods on the `RunDataStore` from [1900](1900_local-run-records.md):
  - `getExecution(executionId): Promise<ContainerRunRecord[]>`, ordered by permutation (in matrix order), then by iteration
  - `getContainerRun(postrunImage): Promise<ContainerRunRecord | undefined>`
- `thunderjar show <test case | execution | container run>`. The argument resolves in this order: a postrun tag, then an execution ID, then a test case name, which means its latest execution (the first from `listExecutions`). Anything else is an error that names the argument, with a non-zero exit.
- The execution view prints one block per permutation. Rows are the measures, sorted by name, which is the same order `run` uses in [2000](2000_first-measurement.md) and [2100](2100_more-instruments.md). Columns are iterations, and values use the same format as `run`. A `skipped` measure prints `skipped`, an errored one prints `error`, and a measure a run doesn't have prints `—`. Below the measures are the exit code and duration of each iteration.

- The container run view gives the reason for a `skipped` measure and the message for an `erroredWhileMeasuring` one, as in the spec's example.

Out of scope (story numbers are backlog positions): aggregates per permutation (story 15); marking stale measures (story 16, which can compare each stored `contentHash` against `hashMeasurement`); cost and tokens (story 17); comparing executions (story 19); `--json` (story 29, with the other non-interactive output).

**Spec gaps.**

- The backlog calls this command `report`, but the spec has `show` and `compare`. This story builds `show` and adds no `report` command. Backlog stories 15 and 19 mean `show` and `compare`.
- The spec's `show <execution>` prints only aggregates, so it has no per-iteration view of an execution. This story's table stands in until story 15, which decides whether the aggregate column sits beside the iteration columns or replaces them.
- The spec doesn't say how `show` tells a test case name from an execution ID. This story tries the ID first, so a test case named like an execution ID would be shadowed.

## How to test

- Store tests run against a per-test temp file. `getExecution` returns records in permutation and iteration order. `getContainerRun` finds a record by its postrun tag, and returns `undefined` for a tag it doesn't know.
- CLI tests use the fake harness, with the ULID generator and clock stubbed. Each runs `run` first, then asserts stdout exactly as above for:
  - `show <test case>` after two runs, which picks the later execution
  - `show <execution ID>` and `show <container run>`
  - a run whose `cli` exits `3`, which shows its exit code and measures
  - an instrument that throws, which shows `error` in the table and its message in the container run view
  - an unknown argument, which prints an error and exits non-zero
